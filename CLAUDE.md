# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root. `SECRET_KEY` has no default and must be set (via `.env` or the environment), otherwise settings fail to import.

```bash
export SECRET_KEY=dev-secret          # or copy .env.example to .env
python manage.py migrate              # SQLite by default (db.sqlite3)
python manage.py runserver
python manage.py seed_demo_data       # idempotent demo company + owner (lives in tenants/)
python manage.py seed_cultural_events # idempotent placeholder CulturalEvents (lives in demand/)
python manage.py seed --fixture x.json  # snapshot into an empty DB + superuser from DJANGO_SUPERUSER_* (tenants/)

pytest                                # whole suite (use this, not `manage.py test`)
pytest authentication/tests.py::PasswordResetConfirmTests::test_valid_token_resets_password
pytest -k tenancy
pytest --cov=authentication --cov=common --cov-fail-under=70   # the CI gate

python manage.py makemigrations --check --dry-run
python manage.py spectacular --file schema.yml                 # OpenAPI; should print no errors/warnings
celery -A config worker -l info       # needs Redis; `celery -A config beat` for the schedule
ruff check .                          # CI lint step (config in ruff.toml)
```

`manage.py test` also works, but CI and the Makefile use pytest. A local `venv/` is git-ignored; API docs are served at `/api/docs/`.

## Architecture

Django 5.2+/DRF monolith. `config/` is only the project package (settings, urls, asgi, wsgi, celery); every app is a top-level directory. 

**Multi-tenancy is by company, not by schema.** `tenants.Company` is the tenant; `AUTH_USER_MODEL = tenants.CustomUser` (email login, has a `company` FK). `common/tenancy.py` is the single source of truth: `TENANT_LOOKUPS` maps each tenant-owned model to the ORM path reaching its company (e.g. `StockMovement -> batch__product__company`).
- Viewsets for tenant data must use `TenantScopedMixin` (filters the queryset, stamps `company` on create, requires a company) and serializers must extend `TenantModelSerializer` (limits related-object fields to the user's company, makes `company` read-only). Other companies' rows are 404, never 403.
- Adding a tenant-owned model means adding it to `TENANT_LOOKUPS`; a test in `common/tests/test_tenancy.py` fails if a lookup path is wrong.
- Shared reference data (`ProductCategory`, `CulturalEvent`, `PricingPlan`, `demand_calendar`) is unscoped: viewsets use `IsStaffOrReadOnly`.
- Superusers bypass scoping; users with no company get 403. The company always comes from `request.user.company` (loaded from the DB), never from a token claim.
- The Django admin is scoped the same way: `TenantAdminMixin`, applied to explicit admins and auto-registered for every other `TENANT_LOOKUPS` model in `common.apps.CommonConfig.ready()`; `CustomUser` has a dedicated `CustomUserAdmin` in `tenants/admin.py` that hides superusers, `is_superuser`, groups, permissions and `company` from company staff (anti-escalation; covered by `CustomUserAdminTests`).
- Default DRF permission is `IsAuthenticated`. Only login, password-reset confirm, invitation accept and verify-email-token are `AllowAny`.

**Auth.** `POST /auth/login/` returns a short-lived HS256 access token (signed with `SECRET_KEY`, `authentication/jwt_handler.py`) plus an opaque refresh token. `authentication.authentication.JWTAuthentication` is the first DRF authenticator, followed by session and basic; unauthenticated requests therefore get 401. Refresh tokens (`authentication/refresh_tokens.py`, model `RefreshToken`, only a SHA-256 stored) are single use: `POST /auth/token/refresh/` rotates within a "family", and replaying a used token revokes the family. Both token types embed/store a stamp of the password hash (`password_stamp`), so any password change invalidates every earlier token. `POST /auth/logout/` revokes a family; access tokens are stateless and live until expiry. Revocation must happen outside `transaction.atomic()` blocks that then raise, or it is rolled back. A token used again within `JWT_REFRESH_REUSE_LEEWAY_SECONDS` of being rotated (and only if the family was not ended by a logout/replay) is answered with a fresh pair instead of revoking the family, so two tabs can race; a session is hard-capped at `JWT_REFRESH_SESSION_MAX_AGE_SECONDS` (`session_started_at` is carried across rotations). A daily Celery task prunes dead tokens.

**Two-factor sign-in.** `authentication/two_factor.py` (rules) and `two_factor_views.py` (HTTP). Required for admins (`is_staff`/superuser), optional for other password users, never for operators. `/auth/login/` calls `login_response(user)`: tokens, or a `TwoFactorChallenge` (`verify` / `enrol`, 5 min, 5 wrong codes, single use, only a SHA-256 stored) traded at `/auth/2fa/verify/` or `/auth/2fa/enrol/` + `enrol/confirm/` (which also work signed in, without a challenge). `TwoFactorDevice.secret` is an `EncryptedTextField`; `last_used_step` stops a code being used twice; 10 failures per user in 15 min (cache `2fa-fail:<id>`) refuse every code; `RecoveryCode` stores SHA-256 of the normalised code. `RefreshView` refuses (and ends) an admin session with no confirmed device. Staff reset someone's 2FA at `POST /auth/2fa/users/<id>/reset/` (`StaffTwoFactorViewSet`, tenant-scoped, not yourself), which revokes their refresh tokens and writes a `TwoFactorEvent` (tenant-owned, read-only admin). Devices, recovery codes and challenges are deliberately not in the admin (`SECRETS` in `common/tests/test_admin_coverage.py`). Recovery codes are stored as an HMAC keyed by `SECRET_KEY` (like operator codes), so rotating it voids them. No password-only way in for admins: `PasswordOnlyBasicAuthentication` refuses Basic for admins and anyone with 2FA on, and the Django admin uses `admin_login.TwoFactorAdminAuthenticationForm` (+ `templates/authentication/admin_login.html`). Only a superuser can reset a superuser. Tests: `authentication/test_two_factor.py`; move the TOTP clock by patching `authentication.two_factor._now`.

**API conventions.** Lists are paginated (`StandardResultsSetPagination`: `count/next/previous/results`, `page_size` capped at 100) and viewsets must have a deterministic order (the tenancy mixins fall back to `pk`). Non-validation errors are `{code, message, status_code}` via `common.exceptions.custom_exception_handler`; validation errors keep DRF's per-field shape.

**App layout.** Each app follows models / serializers / views (ModelViewSets) / urls (`DefaultRouter`). URL prefixes are in `config/urls.py` (`auth/`, `inventory/`, `sales/`, `demand/`, `calendar/`, `logistics/`, `pricing/`, `sync/`, `common/`). `common` also holds cross-app pieces: `DemandAlert`/`StockAlert` models, business `services/` (price recommendation, cost calculation, HMRC tariff, Hijri calendar, Shopify, verification tokens), the websocket consumer (`consumers.py`, `routing.py`), and `tenancy.py`.

**Background work.** Celery tasks live in each app's `tasks.py` (autodiscovered): `common` (low-stock and demand alerts), `logistics` (freight rates), `pricing` (`sync_approved_prices` pushes approved `PriceChangeLog`s to Shopify via `ShopifyService`), `sync`, `authentication` (prunes dead refresh tokens). The beat schedule is defined in `config/celery.py`. `config/__init__.py` imports the Celery app.

**Realtime.** `config/asgi.py` routes websockets through `common/routing.py`. `/ws/sync/` (`sync.consumers.SyncStatusConsumer`) is the web app's live storefront sync status: the access token comes as the subprotocols `["bearer", <token>]` (browsers cannot set headers on a websocket; a query string would end up in logs) with the same checks as `JWTAuthentication`, operators and users without a company are refused (accepted, then closed with 4401 so the web app refreshes its token); on connect the user joins only their company's group `sync-status-<company id>` and gets `sync.status.status_for` (`state` off/green/amber/red, `as_of`, `last_push_at`, `backlog`, `failed`, `last_error` = status line only, never m18's response body). Before every message the consumer re-checks the token's expiry and the user (active, same password, same company) and closes with 4401 otherwise, so a leaver or a moved user hears nothing more. The retry sweep broadcasts once per company. `sync.status.broadcast(company_id)` (never raises) runs after every delivery attempt and after a stock push that sent something. The channel layer is in-memory unless `USE_REDIS_CHANNELS=True`, which workers need too (they broadcast); its Redis `socket_timeout` must stay above channels-redis's 5 s blocking read (redis-py 8 defaults to 5 s, which killed idle consumers). Consumer tests use `TransactionTestCase`: `database_sync_to_async` closes the test's connection on Postgres. Docker timing check: `scripts/e2e/sync_status.sh` (workspace).

**Demand planning.** `common.tasks.scan_demand_alerts` generates `DemandAlert`s from upcoming `demand_calendar.Event`s (product categories x multiplier) and `demand.CulturalEvent`s (products linked via `EventProductKeyword`, multiplier from the company's `cultural_event_multiplier` `Setting`); demand is estimated from outbound `StockMovement`s (`inventory/projections.py`, also behind `.../stock-projection/`). Alerts are unique per product and event, so the scan is idempotent. `GET /common/api/alerts/demand/` lists the company's alerts (open by default, `?status=handled|all`), `.../create/` and `.../dismiss/<pk>/` write them. `demand_calendar.sync_islamic_events` fills the calendar from `HijriCalendarService`.

**Point of sale.** The `sales` app runs the tills. A `TillSession` is a shift (open with a cash float, one open session per till, close with a cash count; `expected_cash` and the variance are frozen at close). A `Sale` is rung up against the open session (`POST /sales/sales/`, items are `{product, quantity}` or, for weighed products, with `weight_kg` (see Weighed products); prices always come from the product; send a `client_ref` UUID so a retry after a lost response returns the original sale with 200 instead of charging twice): stock is taken from the product's batches oldest expiry first, expired batches are never sold, each take is an outbound `StockMovement`, and `SaleAllocation` remembers the batches so `POST /sales/sales/<id>/void/` can put the units back with inbound movements. Cash sales need `amount_tendered >= total` (change is computed). Card sales are taken on a standalone terminal (G36):
they need `card_auth_code` (the terminal slip's auth code, 4–12 letters or digits, stored in capitals) and may carry
`card_last4` (exactly 4 digits, never more of the card number); a cash sale with either is a 400
(`sales.serializers.card_details`). Offline sales (G28) are never refused for these: the code is kept as sent
(capitals), and a last 4 that isn't 4 digits is dropped. Closing takes an optional `counted_card`, the terminal's
end-of-day total; `expected_card` (completed card sales) is frozen at close like `expected_cash`, and the summary's
`card_variance` = `counted_card − expected_card` (null when no total was entered). Tests:
`sales/tests/test_card_terminal.py`. Voiding is for staff or the sale's own cashier, and only while the session is open; closing is for the opener or staff. Products with stock but no batch can't be sold. Business logic is in `sales/services.py`, not the views.

**Operators and roles.** Some people work in one area and sign in with an 8-digit code instead of an email and password: `CustomUser.role` is one of `till`, `demand`, `freight`, `supplier`, `stock` (`tenants/roles.py`; regular and staff users have no role and see everything their permissions allow). Staff create them at `POST /tenants/operators/ {name, role}`; the code is generated (never chosen, because a "taken" error would reveal other companies' codes), returned once, and stored only as an HMAC (`code_hash`, `tenants/operator_codes.py`), so a forgotten one is replaced with `POST .../<id>/reset-code/`. Resetting a code, changing a role (`PATCH`) or deactivating (`is_active`) ends the operator's sessions; operators are never deleted, so their work stays attributed. They sign in at `POST /auth/code-login/ {code}` (throttled harder than passwords, `CODE_LOGIN_THROTTLE_RATE`, 5/min) and get the normal token pair. `authentication/role_access.py` is a default-deny allow-list of what each role may call (e.g. freight: `/logistics/*`; supplier: suppliers, invoices; till: products, tills and its own sessions/sales); `JWTAuthentication` enforces it on every request, so a new endpoint is closed to operators until it is listed there, and tenancy plus each viewset's own permissions still apply. In `sales`, a till operator only sees their own sessions and sales. `GET /auth/me/` returns `role` and `role_label`.

**Importing products (linking the shop's catalogue).** `python manage.py import_storefront_products [--company M18-DEMO] [--dry-run] [--file saved.json] [--api-url URL]` links every m18 product to an IQ product (`sync/catalogue.py`). Without `--file` it reads the shop's public product API at the company's `StorefrontConnection.base_url` + `shop/api/` and the barcodes from the signed `integration/stock/` snapshot (`sync.tasks.storefront_snapshot`; the public API hides the main barcode); a failed snapshot or no connection stops it before anything is written. Per m18 product, in order: already linked (`Product.external_id` = shop id) → `updated` (name, description, category, and price unless the connection has `push_prices` or m18 has no price; never stock); a `sync.StorefrontExclusion` → `excluded`; no price or inactive → `skipped`; one unlinked IQ product with the same barcode (`Product.barcode`, main or alternate) → `linked_barcode`; one with the same name (case and spacing ignored, pack size added by `product_name`; not one whose own barcode differs from m18's) → `linked_name`; otherwise `created` with one `OPENING` batch if it has stock (expiring `--expiry-days` from today). Several matches → `ambiguous`, nothing written. Linking keeps IQ's own name, price and stock (fills a blank barcode), but from the next run the product is `updated`, so m18's name, description, category and (without `push_prices`) price replace IQ's; with `push_prices` on, the next sweep then sends IQ's price to m18. An IQ product already claimed earlier in the run is not a candidate. Every run, dry or not, is saved as a `sync.CatalogueImport` with one `CatalogueImportItem` per m18 product and prints `m18 products: N — linked L, excluded E, needs attention A` (attention = ambiguous + skipped). In the admin, staff link an ambiguous/skipped item to an unlinked IQ product (dry-run rows too: they are real m18 products) or "Mark not sold online" (ambiguous/skipped items only); both record who and when, and the next import reflects them.

**Storefront (m18) integration.** The m18 shop is a separate service; nothing is shared but signed webhooks. A company has at most one `sync.StorefrontConnection` (its `webhook_secret` is set only in the admin and never shown again). The shop posts `order.paid` events to `POST /sync/inbound/storefront/<connection id>/` (`sync.views.StorefrontInboundView`). That route has no user: the only authentication is the `X-Integration-Signature` header (`sync/signing.py`, HMAC-SHA256 over `"<t>." + raw body`, 300 s window, kept in step with m18's `shop/integration/signing.py`), so it is outside `role_access` and the OpenAPI schema. A missing or inactive connection and a bad signature get the same 401. Each event is stored once as an `InboundEvent` (unique per connection and `event_id`), so a redelivery answers `{"status": "duplicate"}`. Items are matched by `Product.external_id` within the connection's company and taken with `inventory.ledger.take_fefo` (the same FEFO code the till uses). A validly signed event always gets 200, because the order is already paid: an unknown product or a malformed item is `unmatched`, too little stock takes what exists and is `partial`, and `detail` records each problem. Review them in the admin (`InboundEvent`, read-only). To rotate the secret, change it on the connection and on the shop's `IQ_WEBHOOK_SECRET` together; the shop redelivers anything rejected in between.

**Storefront loyalty at the till.** Loyalty accounts live in m18. `POST /sync/loyalty/lookup/` (`sync.loyalty.lookup`; the `till` role may call it) makes one signed call to the connection's `base_url` + `rewards/api/integration/lookup/` with a 1.5 s timeout: 503 `loyalty_unavailable` on a timeout or error (the till sells without points), 404 `not_found`, 409 `not_configured` with no active connection. Hits are cached 60 s under a hash of connection and card. A sale with a `loyalty_barcode` writes a `loyalty.award` `sync.OutboundEvent` in the sale's transaction (`sync.outbox.emit`), and a void writes `loyalty.reverse`; both use `order_reference` `iq-sale-<client_ref or sale pk>`, which m18 de-duplicates on. `emit` queues `sync.tasks.deliver_outbound_event` on commit (a broker failure is logged, never raised into the sale), and beat runs `deliver_outbound_events` every 30 s to retry with backoff `min(2**attempts, 3600)` s, `failed` after 20 attempts. Outbound events are read-only in the admin. This needs a Celery worker *and* beat for IQ (`celery -A config worker -B`, or separate beat); without beat a failed send is never retried. The backoff means a short m18 outage catches up within about 30 s, but after a long one the next attempt can be up to an hour away (≈1 h after attempt 12). In local runs, give IQ and m18 different Redis databases (`CELERY_BROKER_URL` vs m18's `REDIS_URL`), or each worker picks up the other's tasks.

**Storefront stock (IQ → m18).** IQ owns stock for products linked to the shop (`external_id` set, company has an active `StorefrontConnection` with a `base_url`). Online available = in-date batch stock at active, `online_sellable` locations (the same ones web orders take from) − `Product.online_buffer` ("keep for shop"), never below 0 (`sync.stock.online_available`); saving a `Location` (e.g. switching `online_sellable` or `is_active`) queues every linked product with stock there (`sync.stock.mark_location_changed`; a queryset `.update()` skips it). Both use `inventory.ledger.ONLINE_LOCATION`. After deploying G10, run `manage.py push_storefront_stock` once so m18 drops stock held at non-online locations straight away (otherwise the 00:30 resend does it). End-to-end check: `scripts/e2e/online_stock.sh` (workspace). Receivers in `sync/signals.py` (new `StockMovement`, `StockBatch` save/delete, `Product` save) mark the product's `sync.StockSyncState` pending in the same transaction (`sync.stock.mark_changed`, an upsert that never fails the caller's write). Note that `ledger.move` and the movement serializer change stock with `.update()`, so it is the `StockMovement` row that triggers this, not the batch. Beat runs `sync.tasks.push_storefront_stock` every 15 s: pending products go out as absolute snapshots `{"product_id", "online_available", "version"}` in `stock.changed` outbox events (500 per event; `version` +1 per send, so m18 ignores older ones). Events go to m18's single `integration/events/` endpoint. Nightly at 00:30 UTC, `reconcile_storefront_stock` fetches m18's figures (`integration/stock/`), stores a read-only `StockReconciliation` report (`different` / `missing_in_m18` / `not_linked_in_iq`), then queues every linked product so the next sweep resends all (fixing drift and overnight expiry). First rollout: `manage.py push_storefront_stock`.

**Storefront prices (IQ → m18).** With `StorefrontConnection.push_prices` on (default off; switching it on in the admin queues every linked product), each `stock.changed` item also carries `"price": "12.99"` = `Product.price`, so a price approved through `PriceChangeLog` (or edited any other way) reaches m18 on the next 15 s sweep under the same per-product version. m18 then owns nothing about that price: it blocks edits and skips the product in its EPOS CSV sync, and refuses prices outside 0 < p ≤ 999.99 (its column cap) for that item only. The nightly report adds `price_different` rows whenever m18 returns a price, on or off, so differences can be checked before switching on. Every switch of `push_prices` writes a `sync.PricePushChange` (on/off, who, when; `StorefrontConnection.save` compares with the stored value, and the admin sets `changed_by`), read-only in the admin. `manage.py price_push_readiness --company <reg> [--top N]` prints the switch history, the latest report's price differences (largest gap first), linked products m18 would refuse (≤ 0 or > 999.99) and `Ready: yes/no`; the go-live steps are in the workspace `docs/runbooks/price-push.md`. Switching off does not hand prices back to m18 (it keeps `iq_price_managed`); the runbook says how. `PriceChangeLog.is_processed` remains Shopify-only.

**VAT.** The `vat` app holds one shared UK rate table (`VatRate(code, rate %, valid_from)`; codes zero / reduced / standard / exempt; seeded by a reversible migration: 0, 0, 5 from 1997-09-01, 20 from 2011-01-04). It is reference data, not tenant data: `/vat/rates/` is read-only and only superusers change rows in the admin, and rows already in force are locked (no edit, no delete): a new rate is a new row with a later `valid_from`. The seed migration's `seed`/`unseed` are tested directly in a plain `TestCase` (a `TransactionTestCase` flush would delete the rates every sale test needs). `Product.vat_code` (default `zero`) picks the rate; the code decides, not the category. Till prices include VAT: `record_sale` rounds each line's gross, takes the VAT out with `vat.services.split_inclusive` (VAT = gross × rate / (100 + rate), half-up to the penny; net = gross − VAT) at the rate in force on the UK calendar day (`vat.services.uk_date()`, Europe/London; the server runs on UTC, so a summer rate change at UK midnight is 23:00 UTC), and stores `vat_code`, `vat_rate`, `net_amount`, `vat_amount` on the `SaleItem`, so later rate edits never change a sale. A code with no rate in force refuses the sale (400). `sales.services.vat_by_rate(lines)` sums rounded lines by (rate, code) for `Sale.vat_summary` and the session summary's `vat_by_rate` (completed sales only); lines sold before G07 have empty VAT fields (`vat_recorded` false, `vat_not_recorded_total`). The schema names the shared choice set `VatCodeEnum` (`ENUM_NAME_OVERRIDES`).

**Locations.** `inventory.Location` (tenant-owned, `TENANT_LOOKUPS` `company`): `code` unique per company (capitals, digits, dashes; the API upper-cases it), `type` (shop floor, butchery, warehouse, back store, van, plus the virtual `in_transit`, `supplier`, `customer`, `waste`, `adjustment`), optional `branch` (required for shop floor, butchery and back store; never for virtual ones), `sellable`, `online_sellable` (needs `sellable`), `is_active`. Each company has exactly one virtual location of each kind (conditional unique constraint), created by the system and read-only in the API. `inventory.locations.ensure_default_locations(company)` adds whatever is missing (the five virtual ones and a sellable, online-sellable `SHOP-<branch id>` shop floor per branch, `SHOP-<id>-2`... if the code is taken); it runs from `post_save` on a new `Company` (all) or `Branch` (only that branch, so a shop floor deleted on purpose elsewhere stays gone) in `inventory/signals.py`, from `manage.py seed` inside the load's transaction, and as frozen code in the reversible data migration `inventory.0010_default_locations` (backwards removes only those defaults). `/inventory/locations/` is readable by any company member and the `stock` role (for the G13 transfer/requisition screens) and changed only by staff (`IsCompanyStaffOrReadOnly`; filters `type`, `branch`, `sellable`); other operators get 403. `Location.branch` is `RESTRICT`: deleting a company removes its locations, but a branch with locations cannot be deleted on its own (retire it with `is_active`; the branches API answers 409). The admin is scoped (`LocationAdmin`) with virtual locations view-only. Batches and movements reference locations (`PROTECT`) from G09.

**Stock ledger.** `StockMovement` is append-only (create/list/retrieve; no edit or delete, and read-only in the admin). Every `StockBatch` is one lot at one `location` (unique `(product, batch_number, location)`; the same lot in two places is two rows), and every movement has `source_location` and `destination_location`: inbound adds to its batch (destination = the batch's location), outbound takes from it (source = the batch's location), and the other side is the counterpart — a virtual location (SUPPLIER, CUSTOMER, WASTE, ADJUSTMENT, IN-TRANSIT) or another real one. So stock moved by the ledger balances per location (in − out); batches created with a quantity (batch API, catalogue OPENING) start without a movement, as before G09. `inventory/ledger.py` is the only door: `move(batch, qty, type, *, counterpart)` (same company only, `LedgerError` otherwise; returns the movement) and `take_fefo(product, qty, *, locations, destination, today=None)` (in-date batches at those locations only, by expiry, then receive date, then pk; batch rows locked), plus `virtual_location`, `sellable_locations(branch)`, `online_locations(company)` and `primary_location(company, create=False)` (oldest branch's shop floor; with `create`, a sellable `MAIN` if none). The till sells from its branch's active sellable locations to CUSTOMER and a void returns each unit to its original batch; storefront `order.paid` takes from the company's online-sellable locations. `POST /inventory/movements/` goes through `move` (inbound from SUPPLIER, outbound to ADJUSTMENT; the location fields are read-only) and an outbound larger than the batch is a 400. `GET /inventory/batches/` filters `?location=` and `?product=` (the Inventory screen's stock per location). `POST /inventory/batches/` takes a `location` (the company's, not virtual); left out, the company's only shop floor is used, otherwise 400 "Choose where this stock is received"; it can't be changed by editing the batch (that is a transfer). Creating a batch still does not change `Product.stock_quantity`. The G09 migrations (`0012`–`0014`) put pre-existing batches at the oldest branch's shop floor (a company without one gets `MAIN`) and gave old movements SUPPLIER→there / there→CUSTOMER, without changing any quantity. `manage.py seed` loads a pre-G09 snapshot by placing its location-less batches and movements the same way after the default locations exist. Ledger locks are `select_for_update(of=('self',))` so only batch rows are locked, not the joined location. In tests, `StockBatchFactory` places batches at `primary_location(company, create=True)` and `history_movement(batch, qty)` writes a past movement without changing stock.

**Weighed products (G14).** `Product.sold_by` is `each` (default; the migration set every existing product to it) or `weight`. A weight product needs `price_per_kg` (4 dp) and is either loose (kg only: batches, movements and allocations keep count 0) or `is_catch_weight` (counted pieces that are each weighed; `nominal_weight_kg` is a typical piece). `StockBatch.weight_kg`, `StockMovement.weight_kg`, `SaleItem.weight_kg`/`price_per_kg` and `SaleAllocation.weight_kg` (3 dp) hold the kg; they are 0/null for each products. `sold_by` and `is_catch_weight` can't change while a batch holds stock or a completed sale in an open session could still be voided (400; the admin form doesn't enforce this yet). Ledger: `move(..., weight_kg=)` needs kg for weighed products and refuses it for each ones (`LedgerError`), and writes exact values read from the locked row (an `F()` sum drifts on SQLite, which stores floats), refusing anything that would take a batch below 0 pieces or 0 kg (`LedgerError`). `take_fefo` is each-only; `take_weighed(product, *, quantity, weight_kg, locations, destination)` returns `[(batch, pieces, kg)]`: loose takes kg FEFO, and if the in-date kg is short the gap is booked ADJUSTMENT → the last batch first (so the sale goes through; no in-date kg at all is a `LedgerError`); catch-weight takes pieces FEFO (too few is a `LedgerError` with `available`), splits the line's kg by pieces (cumulative 3 dp half-up rounding, so the shares sum exactly and are never negative), books a batch's kg gap from ADJUSTMENT and sends a batch's leftover kg to ADJUSTMENT when its last piece goes; `weight_kg=None` takes each batch's average kg per piece (web orders). Till lines: each `{product, quantity}`; loose `{product, weight_kg}` (quantity 1); catch-weight `{product, quantity, weight_kg}` (total kg); at most 100 kg per weighing. Weighed lines are never merged; line total = `weight_kg × price_per_kg` half-up to the penny, then VAT as usual; `unit_price` is the price per kg rounded. A void puts each allocation's pieces and kg back (gap adjustments stay). Receiving (`POST /inventory/batches/`) needs `weight_kg` > 0 for weighed products, count 0 for loose ones, pieces for catch-weight; manual movements take `weight_kg` too (outbound ≤ the batch's kg; catch-weight may move kg only, and taking a batch's last pieces must take all its kg). Web orders: catch-weight by piece with average kg, loose products are recorded `sold_by_weight` and not taken (the m18 contract is unchanged). Transfers and requisitions refuse weighed products. `Product.stock_quantity` stays a count (0 for loose products). Tests: `inventory/test_catch_weight.py`, `test_ledger_weight.py`, `sales/tests/test_weighed_sales.py`.

**Scale-label barcodes (G15).** `inventory.BarcodeRule` (tenant-owned; `prefix` 1–3 digits starting with 2, unique per company; `item_code_length`; `value_type` price GBP / weight kg; `decimals`; `value_check_digit`; `is_active`) describes a variable-measure EAN-13 layout `prefix | item code | [GS1 value check digit] | value | EAN check digit`; the value takes what is left (`value_length`, 4–6, and 4 or 5 with a value check digit; `layout_error` says what is wrong, used by the serializer and `BarcodeRule.clean`). `inventory/barcode_parser.py` is pure Python (no Django, mirrored by the till's JavaScript in G17): `parse(code, rules)` strips the code, checks 13 digits (`format`), the EAN-13 check digit (`check_digit`), picks the longest-prefix active well-formed rule (`unknown_prefix` = an ordinary barcode) and the GS1 4/5-digit price/weight verifier (`value_check_digit`), and returns `Parsed(rule, item_code, value, price, weight_kg)` as exact Decimals. `inventory/barcode_fixtures.json` is the shared fixture file (rebuild it with `python3 scripts/gen_barcode_fixtures.py inventory/barcode_fixtures.json`, an independent implementation); `inventory/test_barcode_parser.py` keeps 100% branch coverage (`pytest -p no:django inventory/test_barcode_parser.py --cov=inventory.barcode_parser --cov-branch`). `/inventory/barcode-rules/` (`?active=true` for the till): company members and the `till` role read, staff write. Matching `item_code` to a product and pricing the line is G18. The till has JavaScript ports (fe `src/utils/barcodes/`, G17) run against a byte-for-byte copy of the fixtures: `inventory/test_barcode_fixtures_checksum.py` pins its SHA-256 (fe pins the same), so after regenerating, copy the file to fe, update both hashes and run fe's vitest (the byte comparison with fe's copy runs only when `../fe` is checked out, so it is skipped in Docker).

**GS1 element strings (G16).** `inventory/gs1_parser.py` (pure Python, mirrored in JavaScript by G17) reads DataBar Expanded / GS1-128 / DataMatrix scans: `parse_gs1(code, today)` strips spaces, tabs and CR/LF (not `str.strip()`, which also eats GS), a leading symbology id (`]e0`, `]C1`, `]d2`, `]Q3`) and a leading GS, and reads either GS-separated AIs or the bracketed form `(01)…(17)…`. Supported AIs: `01` GTIN (check digit → `check_digit`), `10` batch (≤ 20, GS1 set 82), `11`/`13`/`15`/`17` dates (`YYMMDD`, day 00 = month end, GS1 sliding century; bad → `date`), `310n` kg (n 0–5; 3 dp unless the label has more), `392n` GBP (n 0–3, whole pence or `value`). Anything else is `unknown_ai` (incl. `393n`, `320n`); a repeated field, bad characters or truncation is `format`. A variable field runs to the next GS or the end and is never split by guessing: overrunning its maximum is `format` (rescan), and with no separators a short batch followed by a price reads as one batch (fixture `short_batch_swallows_price`). Returns `GS1Parsed(gtin, batch, weight_kg, price, expiry, best_before, expired, elements)`; `expired` = AI 17 before `today`. `inventory/barcodes.py`: `products_for_gtin(company, gtin)` matches `Product.barcode` (trimmed) against the GTIN-14 and its GTIN-13/UPC-12/EAN-8 forms (several can match), and `read_gs1(company, code, today=None)` parses (today = the UK date) and looks up. Fixtures are `gs1_cases` in `barcode_fixtures.json`; `inventory/test_gs1_parser.py` keeps 100% branch coverage (`pytest -p no:django inventory/test_gs1_parser.py --cov=inventory.gs1_parser --cov-branch`). No endpoint: the till uses it in G18.

**Scale labels at the till (G18).** A sale line is either `{product, quantity[, weight_kg]}` or `{barcode}` (the raw scan, ≤ 64 characters, not trimmed, nothing else on the line). `CreateSaleSerializer.validate` reads every barcode with `sales.labels.read_label(company, code, uk_date())` for the session's company: 13 digits → the company's active `BarcodeRule`s and `Product.plu` (digits, unique per company, stored without leading zeros; the item code matches after its zeros are stripped), otherwise GS1 → `products_for_gtin` (several matches refused); a bad check digit, an unknown PLU/GTIN, an expired GS1 use-by, a weight label on an each product, a weighed product's label with no weight or price, or kg outside 0.001–100 is a 400 the cashier can act on. A price-only label on a weighed product gives kg = price ÷ `price_per_kg` (3 dp half-up). `record_sale` charges the label's price when it has one (else weight × £/kg, or `product.price` for an each product), never merges label lines, checks each-product label units with the plain lines for stock, and stores `SaleItem.barcode`, `label_price`, `expected_price` (today's price: `product.price`, or weight × £/kg for a weighed label carrying both weight and price; null when there is nothing independent to compare) and `label_price_flagged` (|label − expected| > expected × the company `Setting` `label_price_tolerance_percent`, default 10, /100). Flagged lines are sold (the customer saw that price); the admin filters `SaleItem` by the flag. Tests: `sales/tests/test_labels.py`, `test_label_sales.py`, `inventory/test_product_plu.py`; Docker check `scripts/e2e/scale_label_setup.py` / `_check.py` / `_teardown.py` (workspace).

**Typed weights at the till (G19).** A weighed line sent as `{product, weight_kg[, quantity]}` (no `barcode`) is a weight the cashier typed, since there is no scale agent yet (G31): `record_sale` marks it `SaleItem.manual_weight` (the client never sends the flag) and refuses a line over the company `Setting` `manual_weight_max_kg` (default 25 kg; a value that is not a positive number falls back to 25) with a 400 naming the product and the limit. The limit is per line (catch-weight: the line's total kg); label lines keep only the serializer's 100 kg ceiling. Otherwise a typed line is priced, VAT-split and taken FEFO like a weight label. The admin filters `SaleItem` by `manual_weight`. Tests: `sales/tests/test_manual_weight.py`.

**Yield templates (G20).** `inventory.YieldTemplate` (tenant-owned; `name` unique per company; `input_product`, sold by weight, PROTECT; `is_active`; `note`) lists `YieldTemplateOutput`s (`kind` product — a weighed product of the company, not the input, once per template — or waste, a `name` such as Bone with no product; `expected_percent` 0.01–100, 2 dp; `position`). The outputs total at most 100% and need at least one product; `YieldTemplate.percent_totals(outputs)` gives (yield, waste, loss), loss = 100 − the rest. The rules live once in `inventory.models.yield_output_problems` (plus `weighed_product_problem`), used by the serializer and the admin inline formset. `/inventory/yield-templates/` (`?active=true`): outputs nested, sending `outputs` replaces them all; the response adds `expected_yield_percent`, `expected_waste_percent`, `expected_loss_percent`. Company members and the `stock` role read, staff write. Breakdown orders (G21) and cost allocation (G22) start from a template. A product output's `keeps_days` (blank = the input's expiry; refused on waste) sets its breakdown batches' expiry. Tests: `inventory/test_yield_templates.py`.

**Breakdown orders (G21).** `inventory.Breakdown` (tenant-owned; per-company `number` from `transfers.next_number`, shown as `BD-000001`; `client_ref` unique per company) records, in one step, an input batch at an active butchery location cut into its yield template's outputs: `inventory/breakdowns.py#record_breakdown` (input batch row locked; only `ledger.move`) checks the template (active; input and output products still sold by weight), the batch (the template's input product, at that location, not expired on the UK day) and the lines (`BreakdownLine` per template output given: kg > 0, 3 dp, once each; pieces for catch-weight output products; at least one product), then books: the input batch sends the product kg (plus `input_pieces` for a catch-weight input) out to its own location (a conversion in place: source = destination = the butchery location), each product line gets a new batch there (`batch_number` = the reference) and an inbound movement, each waste line goes to WASTE and `loss_kg` to ADJUSTMENT; every movement has `StockMovement.breakdown`. A loose input sends `input_kg` (≤ the batch's kg), a catch-weight one `input_pieces` (kg = the batch's average per piece, 3 dp half-up; the last pieces take all its kg). `loss_kg` = input − outputs − waste exactly; below 0 is refused (no gains), above the template's expected loss (half-up, 3 dp) needs `loss_reason`, at or under it the reason is "Expected loss (template)". An output's expiry is min(UK today + `keeps_days`, the input's expiry); an earlier date may be sent, not a later one or a past one. `void_breakdown` (row locked, reason required) refuses once an output batch holds less than it got, then writes the opposite of every movement. `/inventory/breakdowns/` (list `?status=`, create, retrieve, `.../void/`; a repeated `client_ref` answers 200 with the first; no edit or delete): company members read; staff and the `stock` role record; staff or whoever recorded it void; a `LedgerError` is a 400 and a Postgres deadlock a 409 (nothing saved). The service re-checks that template, location and batch are the company's (superusers are not scoped) and re-checks `client_ref` after taking the batch lock. Demand (`inventory/projections.py`) ignores breakdown movements, like transfers. The admin is view only. Tests: `inventory/test_breakdowns.py`, `test_breakdown_api.py`.

**Breakdown costs (G22).** `StockBatch.unit_cost` (optional, ≥ 0, 4 dp, ex VAT) is the landed cost per kg for weighed products (per unit otherwise), set through `/inventory/batches/` by staff only (read-only for other members and the `stock` role, who still see it; no till or storefront payload carries it). Editing an output batch's cost later does not change its breakdown's `allocated_cost`. A breakdown of a batch with a cost books `Breakdown.input_cost` = `input_kg` × `unit_cost` (half-up to the penny) and spreads it over the product lines by the template's `cost_method`: `weight` (default, by kg) or `value` (kg × `price_per_kg`; an output product with no £/kg, or 0 or less, refuses the breakdown; only when there is a cost to spread). Each share is half-up to the penny and the rounding remainder (either sign) goes on the line with the largest basis (the first of equals; when rounding gave out too much and that line would go below 0, the rest comes back from the next largest, never below 0), so `BreakdownLine.allocated_cost` sums to `input_cost` exactly; waste gets none, and each output batch's `unit_cost` = share ÷ kg (4 dp). No cost on the input batch: no allocation (`input_cost` null). An input cost of £10bn or more is refused (the field's size). `Breakdown.cost_method` records the method used. `inventory.breakdowns._allocate`; tests `inventory/test_breakdown_costs.py`.

**Waste write-offs (G23).** `inventory.WriteOff` (tenant-owned; per-company `number`, `W-000001`) takes stock from one batch (the company's, on a real location) to the company's WASTE location with a `reason` (expired, damaged, trim, quality, theft, sample) and a note: units for each products, pieces for catch-weight (kg = the batch's average per piece, the last pieces take all its kg) or `weight_kg` for loose products, at most what the batch holds; expired batches may be written off. `cost` = amount × the batch's `unit_cost` (kg for weighed), half-up to the penny, null with no cost. `inventory/write_offs.py`: a known cost at or under the company `Setting` `write_off_approval_threshold` (default £50; not a number ≥ 0 → £50) is written off at once; anything above it, or with no known cost, is `pending` with nothing moved until a staff member *other than the one who raised it* approves (batch locked, re-checked: if it no longer holds the amount the approval is refused and a new write-off is needed) or rejects it (nothing moves). The approver sees what was raised: a catch-weight batch whose pieces' kg changed meanwhile (other pieces sold) is refused at approval (reject and raise again), and a later batch cost change does not alter `cost`. A cost of £10bn or more is refused. Every movement carries `StockMovement.write_off`; demand ignores them. `/inventory/write-offs/` (list `?status=`, raise, retrieve, `.../approve/`, `.../reject/` with an optional `note`; no edit or delete): company members read; staff and the `stock` role raise; staff decide. The admin is view only. Tests: `inventory/test_write_offs.py`.

**Yield and waste reports (G24).** `StockBatch.supplier` (optional, the company's `Supplier`, PROTECT) is set on receipt; breakdown output batches take their input batch's, and a lot created at a transfer's destination takes the source lot's (an existing lot keeps its own). `inventory/reports.py` works on UK dates (`vat.services.UK`; `from`/`to` inclusive, weeks from Monday). `yield_report(company, start, end, group)`: completed breakdowns recorded in the range (voided ones are left out; they net to zero in the ledger), grouped by input product, supplier ("Supplier not recorded" when none) or butcher (`created_by`, shown by name, else `User #<id>`; never the email); per output (products by product, waste by name) the actual kg against expected kg = the template output's *current* `expected_percent` × input kg (3 dp half-up per breakdown, as `BreakdownLineSerializer.expected_kg`), the % of the group's input (2 dp) and the variance; plus loss against expected loss the known `input_cost` and `uncosted` (breakdowns without one). `waste_report(company, start, end, group)`: write-offs with status `written_off`, bucketed by the UK date of `written_off_at`, by reason or product: count, quantity (units/pieces), kg, known cost and `uncosted` (no cost). `GET /inventory/reports/yield/` and `/inventory/reports/waste/` (`?from=&to=&group=`; default the last 8 weeks up to today; more than 366 days, `from` after `to` or an unknown group is a 400): staff and the `stock` role. Operators (the `stock` role) read `/inventory/suppliers/` as `id` and `name` only (`SupplierNameSerializer`); a batch's `supplier`, like its `location`, cannot be changed after receipt; deleting a supplier with batches is the usual 409 `Protected`. Tests: `inventory/test_reports.py` (the totals are checked against `StockMovement`), `inventory/test_batch_supplier.py`.

**Till catalogue (G26, ADR `docs/adr/0001-offline-till.md` in the workspace).** `Product.updated_at` is the product's version: `Product.save()` always sets it (a `save(update_fields=…)` gets it added, so price approvals and the storefront import count), and the ledger's `stock_quantity` `update()` sets it to `timezone.now()` (the app clock, like `save()`), so stock changes reach tills. A change stamped more than 60 s before a till's cursor but committed after it (a very long transaction, e.g. a big storefront import) is missed by deltas; the till's full reload every 6 h repairs it. It is not `auto_now` (a loaded snapshot without it gets the default) and not editable. A bulk `Product.objects.update()` of other fields would skip it: add `updated_at=Now()` to any new one. Deleting a product writes `inventory.ProductRemoval` (company, `product_id`, `removed_at`; tenant-owned) from a `post_delete` signal, except when a company delete started it. `GET /sales/catalogue/?since=<cursor>` (`sales/catalogue.py`, `CatalogueView`; the till role, staff and members): `cursor` is the server time at the start of the request; with a readable `since` it sends products and removals changed at or after `since − 60 s` (`full: false`), otherwise everything (`full: true`); always the VAT rates, active barcode rules, active tills, branches and `settings` (`manual_weight_max_kg` via `sales.services.manual_weight_limit`; `offline_warn_hours` 4, `offline_confirm_hours` 24, `offline_stop_hours` 72, a value that is not a whole number above 0 falls back), plus `user` and `company`. Products carry only till fields (`CatalogueProductSerializer`, including `commodity_code` for the till's search); users with no company get 403 (`HasCompany`). `record_sale` must stay `@transaction.atomic` (its row locks need it on Postgres; `sales/tests/test_sale_transaction.py` checks a failure part-way leaves nothing). Tests: `inventory/test_product_versioning.py`, `sales/tests/test_catalogue.py`.

**Branch codes (G27).** `Branch.code` is optional: 2–4 capital letters or digits, not `B` and a number (tills use `B<id>` for a branch with no code), unique per company when set (a conditional constraint plus the serializer check); the serializer upper-cases what is sent (JSON or form). **Offline sales sync (G28, workspace ADR 0001).** `POST /sales/offline-sales/` (`sales/offline_sync.py`; the till role, staff, members; at most 100 per request; `offline_number` required) takes the sales a till kept offline (G27) and records them oldest first (`created_at`, then `offline_number`), each in its own savepoint, one result per sale: `recorded`, `duplicate` (the `client_ref` is already a sale anywhere in the company — also an online charge whose answer was lost; a `void` sent with it is applied then, with a `loyalty.reverse` if it had points) or `error` (not this company's session/product, no VAT rate on the sale's date, no location to sell from, an offline number already used on that session by another sale, or any unexpected failure — logged, never a 500, so one sale can't block the till's queue; it stays on the till). A paid sale is never refused and the till's reading wins: each line is booked as the till sold it (its product, kg and `charged` gross; `unit_price` from it) with VAT at the rate of the sale's UK date (`split_inclusive`; a `created_at` more than 5 min ahead is clamped), and every difference is a `SaleException`: `price` (expected vs charged; labels also set `expected_price`/`label_price_flagged` as online), `stock`, `label` (no longer readable, or now reads as another product), `product_changed` (sold by each/weight then, the other way now; a now-weighed product with no kg takes no stock), `weight_limit`, `tender` (cash below the total), `session_closed` (the sale still goes on it), `cashier`. Stock is taken FEFO now from the branch's sellable locations (rows locked; products locked in pk order like online sales), in date on the sale's day; what isn't there comes through `ledger.take_short` (a `SHORT-<receipt>` batch at the first sellable location: ADJUSTMENT → location → CUSTOMER, so nothing goes negative). A sale voided on the till is recorded as voided and moves no stock and sends no loyalty event (the goods never left); otherwise a scanned card is awarded as online. `services.reverse_sale` is shared with `void_sale` (which keeps its own checks). `Sale.offline_number` (unique per session when set), `sold_at`, `card_auth_code`. `SaleException` is read-only in the admin; managers review them at `GET /sales/exceptions/` (G29; staff only, open ones by default, `?resolved=true`, `?kind=`) and mark each handled with `POST /sales/exceptions/<id>/resolve/` (records who and when; a second resolve is a 400). Tests: `sales/tests/test_offline_sync.py`, `test_offline_models.py`, `inventory/test_take_short.py`; `scripts/e2e/offline_sync.sh` in the workspace.

**Trade customers (G38, B2B wholesale).** The `wholesale` app (M7: price lists, orders and credit build on it). `TradeCustomer` (tenant-owned; `account_code` unique per company, 1–20 capitals/digits/dashes, upper-cased; `legal_name`, optional `trading_name`, optional UK `vat_number` stored without spaces (GB/XI + 9 or 12 digits, or GBGD/GBHA + 3); `status` active/on_hold/closed; `delivery_days` a week-ordered list of `mon`…`sun`; `note`) owns `TradeCustomerAddress` (label, lines, town, UK postcode normalised to `TT1 1TT`, driver instructions; at most one `is_default`, a constraint) and `TradeCustomerContact` (name, role, email, phone; at most one `is_primary`). `/wholesale/customers/` (`?status=`, `?search=` on code and names): list, create, retrieve, update; addresses and contacts are nested and sending either replaces it (a single one becomes the default/primary); no delete — close the customer (orders will point at it). **Price lists (G39).** Trade prices are ex VAT, 4 dp, per unit (per kg for weighed products). `Product.wholesale_price` is the base trade price (optional; staff-only on the product API — popped for members and operators — and not on the till catalogue or any storefront payload). `CustomerGroup` (tenant-owned, name unique per company); `TradeCustomer.group` (at most one; deleting the group sets it to null). `PriceList` (tenant-owned: name unique per company, `priority` -1000…1000, `is_active`, `valid_from`/`valid_to` UK dates inclusive and optional, `customers` and `groups` M2M from the same company; none assigned = a draft that applies to nobody) owns `PriceListEntry` (`product`, `min_quantity` > 0 — whole units for each products, kg to 3 dp for weighed — and `unit_price` ≥ 0; `(list, product, min_quantity)` unique). **Resolving** is `wholesale/pricing.py`: `resolve_prices(customer, [(product, quantity)], on=None)` returns a `ResolvedPrice(unit_price, source, price_list, min_quantity)` or `None` per line, `resolve_price(...)` raises `NoPrice`; `on` defaults to `vat.services.uk_date()`. The endpoint loads all products in one query (its count does not grow with the lines). Members read and may resolve; staff write; operators 403 (not in `role_access`). Tests: `wholesale/tests/test_pricing.py` (table of every fallback step; 200 lines < 200 ms in ≤ 4 queries), `test_price_list_api.py`.

**Sales orders (G40).** `SalesOrder` (tenant-owned; `number` per company via `wholesale.orders.next_order_number` (locks the company row), shown `SO-000123`; `customer` (PROTECT), `delivery_date`, `customer_ref`, `note`; the delivery address **copied** from one of the customer's addresses (`delivery_label`, `line1`, `line2`, `town`, `postcode`, `instructions`), because G38 recreates address rows on edit) owns `SalesOrderLine` (`product` once per order; `quantity` units for each products and pieces for catch-weight, or `weight_kg` for loose weighed products). **Stock allocation (G41).** A confirmed order reserves its lines at its warehouse, `SalesOrder.source_location` (an active `warehouse` location of the company; defaulted when the company has exactly one, required with several, changeable in draft only, needed to confirm). `inventory.StockReservation` (`batch`, `order_line`, `quantity` units/pieces or `weight_kg` for loose products, `released_at`) is **not a movement**: the batch keeps the stock until picking (G42). `inventory/reservations.py`: `reserve(line, location)` tops a line up from free in-date stock FEFO (batches locked) and returns what is still short; `release(order)`; `reserved_amounts(lines)`. In `inventory/ledger.py`, `_fefo_batches` gives each batch `free` (held − active reserved, read after the locks are taken) and skips batches with none, so `take_fefo`, `take_weighed` (a loose last-batch gap is booked on top of the free kg, never into reserved kg; catch-weight's "last piece" still uses the real count) and `transfer_fefo` never take reserved stock — they go short instead. A `move` out of a batch that leaves it holding less than its reservations (a write-off, a short receipt) trims them newest first (a row cut to 0 is released), so reserved ≤ held always. The till's own checks (`sales/services._sellable_batches`, offline replay `_take`) count free stock too: online it says "only N in date", an offline replay books the reserved part short (stock exception), never refused. Reservation-row locks: the trim locks the rows it cuts, so a concurrent release isn't undone. `orders.confirm` reserves after the price snapshot (a shortage doesn't stop it), in product order (no deadlock with tills), only from lots in date on the delivery day, `orders.allocate` (`POST /wholesale/orders/{id}/allocate/`, staff, confirmed or picking only) tops up, `orders.cancel` releases. Lines show `reserved` and `short` (strings: units, or kg for loose; null unless confirmed/picking), the order `is_short`. `sync.stock.online_available` subtracts active reservations at online locations, and saving a reservation queues the storefront push (`sync/signals.py`). Admin: reservations view only. Tests: `inventory/test_reservations.py`, `wholesale/tests/test_allocation.py`.

**Picking (G42).** `Product.storage_zone` (ambient/chilled/frozen/butchery, blank = butchery for weighed products, ambient otherwise: `Product.pick_zone`); `Location.DISPATCH` (real, never sellable; `ledger.dispatch_location(company)` gets or creates `DISPATCH`). `ledger.pick_batch(batch, quantity=, weight_kg=, to=)` moves a picked amount of a locked, in-date lot into the same lot at `to` — only the lot's free part (release the order's own reservations first); recorded kg below the real kg is booked in from ADJUSTMENT first, and a catch-weight lot whose last piece goes sends leftover kg to ADJUSTMENT. `wholesale/picking.py`: `start_pick` (confirmed → picking), `record_pick(order, line_id, user=, batch_number= | barcode=, quantity=, weight_kg=)` → `SalesOrderPick` (lot at the order's warehouse, in date; a label is read by `sales.labels.read_label` = one item with its kg, its lot is this line's reserved lot first, then free FEFO; units/pieces never over the ordered, kg up to 120% of the ordered or estimated kg; never another order's reserved stock; loose kg up to 120% of what the lot has for this order, or exactly that while another order holds part of the lot — `pick_batch` likewise never books a kg gap into a lot others hold; each pick moves the line's reservations onto the picked lot via `inventory.reservations.hold_picked`, so stock in the picker's hands can't be reserved or sold before the finish), `remove_pick`, `propose_substitute` (a new line with `substitute_for`, `substitution='proposed'`, unpriced; one open proposal per line; catch-weight in pieces only, kg estimated on approval; `allocate` skips proposed and rejected swaps), `decide(..., approve=, user=)` (staff, not the proposer; approval prices it via `orders.price_lines` on the delivery date and refreshes the estimates), `finish_pick` (refused while a swap is proposed or nothing is picked; releases the reservations, moves every pick to DISPATCH via `pick_batch` in product then lot order, sets `picked_quantity` / `picked_weight_kg` per line — 0 when nothing was picked — then picked). The unique product-per-order constraint applies to ordered lines only. API on `/wholesale/orders/{id}/`: `start-pick/`, `finish-pick/`, `picks/` (GET, POST `{line, batch_number | barcode, quantity?, weight_kg?}`), `picks/{pick_id}/` (DELETE), `substitutions/` (POST `{line, product, quantity | weight_kg}`), `substitutions/{line_id}/approve|reject/`, `pick-list/` (PDF, `wholesale/pick_list.py`, reportlab: a table per zone in order ambient → chilled → frozen → butchery, by name, with the reserved lots and empty picked/kg boxes; user text escaped). Picking actions are for staff and the `stock` operator role (`MayPick`; the role also has them, plus reading orders, in `role_access`); approve/reject is staff only. Picks are view only in the admin. Lines show `zone`, `picks`, `picked_quantity`, `picked_weight_kg`, `substitute_for`, `substitution`, `proposed_by`, `decided_by`, `decided_at`. Tests: `inventory/test_pick_ledger.py`, `wholesale/tests/test_picking.py` (incl. 50 kg ordered → 51.2 kg picked balances), `test_picking_api.py`.

**Invoices (G43).** `tenants.Company.vat_number` (normalised and checked by `vat/numbers.py`, which also serves trade customers; staff edit it at `/tenants/company/`) — issuing is refused without it. `TradeCustomer.invoice_email` (blank: the primary contact's email) and `payment_terms_days` (0–120, default 30). `wholesale.Invoice` (tenant-owned, one per order, `draft` → `issued`) owns `InvoiceLine`s (`order_line` PROTECT, `description`, `quantity` units/pieces, `weight_kg` real kg, `unit_price`, `vat_code`, `vat_rate`, `net`, `vat`, `gross`). `wholesale/invoices.py`: `create_invoice(order, user)` for a picked/dispatched/delivered order, billed on `picked_quantity` (each) or `picked_weight_kg` (weighed; catch-weight also shows pieces) at the order line's fixed price and VAT rate (never recomputed), net and VAT half up to the penny per line, totals and `vat_summary` (by rate, strings) sums of the lines; nothing picked, proposed/rejected swaps → left out; `refresh_draft`; `issue(invoice, user)` locks the company row, numbers it highest issued + 1 (drafts take none, issued are never deleted → gap-free; `INV-000123`), copies seller/customer (both VAT numbers, address, ref), sets `invoice_date` (`uk_date`) and `due_date` (+ terms), moves a `delivered` order to `invoiced`, and after commit queues `send_invoice_email` (Celery; PDF attached; `email_status` queued/sent/failed/no_address; never raises, never logs the address); `resend`. **Frozen once issued:** `Invoice.save` refuses anything but the email fields; the managers' `update` (Invoice: email fields only), `InvoiceLine` `update`/`bulk_update`/`bulk_create` refuse issued invoices; `Invoice.delete` re-checks under the row lock (`discard_draft` for the API), and a `pre_delete` signal backs it for queryset deletes; `InvoiceLine.save`/`delete` refuse on an issued invoice. Email failures are logged as the invoice number and the error type only (SMTP messages quote the address). The email task is registered through `wholesale/tasks.py`. Superusers reach every company's invoices, as in the other viewsets; creating one still needs an order of their own company. PDF: `wholesale/invoice_pdf.py` (reportlab, `invariant=True`; issued ones read only their own copied fields; drafts say DRAFT). API `/wholesale/invoices/` (list with `?status=`, `?customer=`, `?order=`; retrieve; POST `{order}` → draft; DELETE drafts only; no update) and `issue/`, `refresh/`, `email/`, `pdf/`. Members read; staff write; operators 403; the order must be the user's company's (superusers included). Admin view only. Tests: `wholesale/tests/test_invoices.py`, `test_invoice_api.py` (PDF text snapshot `wholesale/tests/snapshots/invoice.txt`; regenerate on purpose with `UPDATE_SNAPSHOTS=1`).

**Delivery runs (G44).** A new operator role `driver` (`tenants.roles.DRIVER`). `wholesale.DeliveryRun` (tenant-owned; `number` per company `RUN-000001`; `run_date`; `vehicle` = an active `van` Location of the company; `driver` = an active operator of the company with the driver role; `planned` → `out` → `completed`, or `planned` → `cancelled`) owns `DeliveryStop`s (`order`, `position` unique per run, `pending`/`delivered`/`failed`, POD: `received_by`, `delivered_at`, `notes`, `photo`, `recorded_by`, `failed_reason`). `wholesale/runs.py`: `create_run` / `update_run` (`set_stops`) take picked orders of the company, each on at most one planned/out run (orders locked); `start_run` moves each order's picks — found by batch number at DISPATCH — onto the van with `ledger.relocate` (exact units/kg into the same lot; more than held is refused, nothing to ADJUSTMENT) and the order picked → dispatched — first checking that each shared DISPATCH lot still covers every picked order's picks from it, so a shortage stops every run that needs it; start re-checks the van (active, never sellable) and the driver; start, deliver and complete lock products then lots in id order (as tills do); `deliver(stop, user, received_by=, delivered_at=, notes=, photo=)` (staff or the run's driver; the run out, the stop pending) moves them van → CUSTOMER and the order dispatched → delivered (→ invoiced if its invoice is issued); `fail_stop(stop, user, reason)` leaves the stock on the van; `complete_run` needs no pending stop, brings failed stops' stock van → DISPATCH and their orders dispatched → picked (a G44 edge in `orders.TRANSITIONS`, only `complete_run` takes it) — what the van no longer holds isn't brought back, and the order then owes what came back (its picks and lines' picked amounts are lowered, a draft invoice rebuilt); the delivery time must be between the run's start and now (± 5 min); `invoices.issue` reads the order under its lock so a delivery and an issue at once still end invoiced; `cancel_run` (planned). API `/wholesale/runs/` (list `?status=`, `?date=`; create `{run_date, vehicle, driver, orders, note?}`; update planned runs, `orders` re-plans; no delete) with `start/`, `complete/`, `cancel/`, `manifest/` (PDF, `wholesale/manifest_pdf.py`), `stops/{id}/deliver/` (JSON or multipart), `stops/{id}/fail/`, `stops/{id}/photo/`. Staff plan and move runs; members read (not photos; they do see recipient names and addresses, a deliberate choice for the office); a driver's queryset is only their runs (another's is a 404) and `role_access` gives them read, manifest, deliver/fail and photo. POD photos: JPEG/PNG by signature, ≤ `POD_MAX_UPLOAD_BYTES` (5 MB), stored as `pod/<company>/<random>.<ext>`, never shown as a path, served only by `photo/`; excluded from the admin (view only). Tests: `wholesale/tests/test_runs.py`, `test_runs_api.py`.

**Returns and credit notes (G45).** `CustomerReturn` (tenant-owned, `RET-000001` per company, `door` or `later`, `on_van` → `received`) owns `ReturnLine`s — one per order line per lot (`batch_number`, from the order's picks in pick order), `quantity` and/or `weight_kg`, `reason` (`damaged`/`out_of_date` → `waste`; `wrong_item`/`not_wanted` → `restock` at `location`). `wholesale/returns.py`: a line never gives back more than was delivered (picked − refused at the door − returned before); catch-weight pieces and kg go together (all the pieces only with all the kg); each order line once per request (a repeat is refused, or it would pass the cap twice); an out-of-date lot is never restocked to a sellable place; door returns take what is still on the van (a van write-off is the van's to explain); `deliver` and `record_return` lock the company (when a return is numbered) and the order's invoice before the order, as `invoices.issue` does; a draft invoice is dropped at the door only if nothing reached the customer. **At the door:** `runs.deliver(..., refused=[{line, quantity?, weight_kg?, reason}])` records a `door` return (`refuse_at_door`), moves only the rest van → CUSTOMER, and rebuilds a draft invoice (dropped if nothing reached the customer); `complete_run` then takes refused goods off the van (`receive_door_returns`: `relocate` to DISPATCH, or out to WASTE). Invoices bill what was delivered (`returns.delivered(line)`). **Later:** `record_return(order, user, lines, note)` (delivered/invoiced orders; `POST /wholesale/orders/{id}/returns/`, location defaults to the order's warehouse) brings goods back from CUSTOMER into the same lots via `ledger.take_back` — at the location, or into DISPATCH and straight out to WASTE. **Credit notes** (`CreditNote`/`CreditNoteLine`, `wholesale/credit_notes.py`): one per return, against the order's issued invoice (a door refusal made before the invoice was issued was never billed: refused), seller/customer copied from that invoice; each line credits its invoice line at its unit price and VAT rate (units, or kg for weighed), half up, and never beyond what the line billed in units/kg or money — the credit that completes a line takes exactly its remaining net and VAT; the cap is checked again at issue under the invoice's lock. Issued like invoices: `CN-000001` gap-free under the company lock, frozen (the shared `FrozenDocumentQuerySet` / `FrozenLineQuerySet` and save/delete guards), PDF (`invoice_pdf.build_credit_note_pdf`) emailed by `send_credit_note_email` (registered in `wholesale/tasks.py`). API: `/wholesale/returns/` (read; `?order=`, `?kind=`), `/wholesale/credit-notes/` (POST `{customer_return}`, DELETE drafts, `issue/`, `email/`, `pdf/`). Members read; staff write; drivers only refuse at the door through `deliver`; other operators 403. Admin view only. Tests: `wholesale/tests/test_returns.py`, `test_credit_notes.py`, `test_returns_api.py`.

**Customer ledger (G47).** What a trade customer owes is the sum of their `wholesale.LedgerEntry` rows (tenant-owned via `customer__company`), never a stored balance. `amount` is signed, 2 dp: positive = owed more (`invoice`, a debit `adjustment`), negative = owed less (`credit_note`, `payment` for G49, a credit `adjustment`); check constraints pin the sign and document per kind, `amount <> 0`, and an adjustment needs a `reason`. `invoices.issue` and `credit_notes.issue_credit_note` post the gross total (on the document's date, described `Invoice INV-…` / `Credit note CN-…`) inside their transaction via `wholesale/ledger.py` (`post_invoice`, `post_credit_note`; OneToOne, so once per document; a £0 document posts nothing). `post_adjustment(customer, amount, reason, user)`: staff only, a Decimal to the penny, not 0, at most £999,999.99 either way, dated the UK day; adjustments never touch VAT (that is a credit note) and a mistake is corrected by the opposite adjustment. **Append-only:** `save` of an existing row, `delete`, a `pre_delete` signal and the queryset's `update`/`delete`/`bulk_update`/`bulk_create(update_conflicts=True)` all refuse (`LEDGER_FROZEN`), and `base_manager_name = 'objects'` so no internal path gets a plain manager; the back-fill migration `0011_backfill_ledger` (posts issued documents that have no entry; idempotent) uses `_base_manager` and `_raw_delete` on the way back. `ledger.balance(customer, on=None)` and `statement(customer, start, end)` (`opening`, entries each with `running`, `closing`). API: `GET /wholesale/customers/{id}/ledger/?from=&to=` (default the 90 days to today, at most 366), `POST /wholesale/customers/{id}/adjustments/` `{amount, reason, client_ref?}` (staff; the same `client_ref` again answers 200 with the first entry, with a different amount or reason 409), both 404 for another company's customer even for a superuser; the statement answers `start`/`end`; and `balance` on every customer (one Subquery in the list). Members read; operators 403 (not in `role_access`). Admin view only. Tests: `wholesale/tests/test_ledger.py`, `test_ledger_api.py`.

**Transfers.** `inventory.Transfer` (tenant-owned; `number` per company from the highest one + 1 with the `Company` row locked, shown as `T-000042`) moves stock between two of the company's own real, active, different locations: `draft` → `dispatched` → `received`, or `draft` → `cancelled` (only a draft; a dispatched one is closed by receiving it, 0 if nothing came). `TransferLine` is one product and a count (weighed products are refused, G14); `inventory/transfers.py` holds the flow and calls only the ledger. Dispatch re-checks the route, then per line `ledger.transfer_fefo` takes in-date batches at the source, earliest expiry first, into the same lots (number and expiry) at the company's IN-TRANSIT location; a short line raises before anything moves (400 "<product>: only N available at <code>."). `TransferPick` records which IN-TRANSIT batch got how much, because two transfers of one lot share that row. Receive takes every line once (`received_quantity` 0..sent, a reason when different; no over-receipt, one receipt): arrived units go on into the same lot at the destination (`ledger.transfer_batch`), the rest IN-TRANSIT → ADJUSTMENT. Every movement it writes has `StockMovement.transfer`, and demand (`inventory/projections.py`) ignores those. Each step locks the transfer row and checks its status, so a repeat is a 400. `/inventory/transfers/` (list `?status=`, create, retrieve, update/patch a draft; sending `lines` replaces them; no delete) with `.../dispatch/`, `.../receive/`, `.../cancel/`; staff and the `stock` role. Admin: view only. A lot that expires on the road is still booked in (tills and online never take expired stock). Tests: `inventory/test_transfer_ledger.py`, `test_transfers.py`, `test_transfer_api.py`.

**Requisitions.** `inventory.Requisition` (tenant-owned; per-company `number` from `transfers.next_number`, shown as `R-000042`) is a store location (`location`: the company's, active, a shop floor, butchery or back store) asking for stock, with one `RequisitionLine` (product, count) per product. It never moves stock: `POST /inventory/requisitions/<id>/fulfil/ {source_location, lines: [{line, quantity}]}` (`inventory/requisitions.py#fulfil`, requisition row locked) makes a draft G11 transfer from `source_location` to the requisition's location whose lines point back through `TransferLine.requisition_line`; each amount is at most the line's `open_quantity`, lines left out stay open, so fulfilling in parts is several transfers. A line's `fulfilled_quantity` is the units on its transfers except cancelled ones (a short receipt still counts: the shortfall went to ADJUSTMENT), and the stored `status` (`open` → `partly_fulfilled` → `fulfilled`, or `cancelled`) is recomputed by `refresh_status` after a fulfil and when one of its transfers is cancelled (its units open again). `cancel` closes what is still open; transfers already made stay. A transfer made from a requisition keeps its lines and destination (`replace_draft` refuses; cancel it and fulfil again; sending no `lines` in a PATCH keeps them, so edit such a transfer with PATCH of `source_location`/`note`; a PUT always sends `lines` and is refused; `TransferLine.requisition_line` is shown read-only). `/inventory/requisitions/` is list (`?status=`), create, retrieve plus `fulfil`/`cancel` (no edit or delete); staff and the `stock` role. Admin: view only. Tests: `inventory/test_requisitions.py`.

**Pricing.** `PriceChangeLog` is a *request*: clients cannot set `is_approved`/`is_processed`/`old_price` or any of the decision fields. The server stamps `source` (`manual` from the API, `decay_markdown` from the nightly job) and `requested_by`. The `approve` action applies `new_price` to the product (409 if the price moved or the change was rejected) and only then does `sync_approved_prices` push it to Shopify; `reject` keeps the row (`is_rejected`, 409 once approved). Both lock the row, take an optional `{"note"}` and record `decided_by`/`decided_at`/`decision_note`; decided rows cannot be deleted (only pending ones can be withdrawn). Both are staff-only (`IsCompanyStaffOrReadOnly`) and closed to operators (not in `role_access`; the `stock` role may only read the list). `PriceRecommendationService.propose_decay_markdowns` (nightly) only proposes; one batch per product (the nearest to expiry) drives its price; it ignores rejected rows and skips a markdown already rejected at the same old/new price. Invoice files are validated by extension *and* magic bytes, stored under a random name, and served only by an authenticated endpoint.

**Per-company uniqueness.** `TenantModelSerializer` also checks unique constraints that include `company` (DRF skips them because `company` is read-only), so use `UniqueConstraint(fields=['company', ...])` and the duplicate becomes a clean 400.

**Email.** `authentication/emails.py` sends invitation and password-reset links (templates in `settings.INVITATION_ACCEPT_URL` / `PASSWORD_RESET_URL`); a mail outage is logged, never raised.

**Encrypted fields.** `common.fields.EncryptedTextField` (Fernet, keys from `FIELD_ENCRYPTION_KEYS`, falling back to a key derived from `SECRET_KEY`) is used for `ShopifyConnection.access_token` and `TwoFactorDevice.secret`; it cannot be filtered on, and legacy plaintext values still read fine.

**Static files** are served by WhiteNoise (`STATIC_ROOT=staticfiles/`, collected in the Docker build).

**Settings** read everything through `python-decouple` (`.env`). External-service settings (`HMRC_*`, `FREIGHT_RATES_API_URL`, `RATE_CHANGE_THRESHOLD`, `DEFAULT_CUSTOMS_DUTY_RATE`, `REDIS_*`) are listed in `.env.example`.

## CI/CD

GitHub Actions only (there is no CircleCI config). `ci.yml` has `test` (Postgres, missing-migration check, coverage gate), `lint` and `docker` jobs. `deploy.yml` runs via `workflow_run` after CI passes on `main`: build, push to ECR (tag = commit SHA), rewrite the ECS task definition's images with `jq`, update the service. It skips with a warning unless `AWS_ROLE_ARN`, `AWS_ECR_REPOSITORY_URL`, `AWS_ECS_CLUSTER`, `AWS_ECS_SERVICE` (secrets) and `AWS_REGION` (variable) are set. With the repository variable `ECS_RUN_MIGRATIONS=true` it first runs `migrate` as a one-off ECS task on the new revision (reusing the service's network config) and aborts the deploy if that fails; it always enables the ECS circuit breaker and fails the job unless the NEW task definition is the PRIMARY deployment with `rolloutState=COMPLETED` (a rolled-back service otherwise looks stable). The shell blocks were verified with a stand-in `aws` CLI, not real AWS. Validate workflow edits with `docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest`. Setup details are in the README.

## Gotchas

- Migrations are a fresh initial set; most apps have a `0001_initial` plus `0002_initial` because of cross-app foreign keys (`authentication` and `sync` add later migrations on top). Delete any old local DB rather than migrating it forward.
- Docker: `docker compose up --build` runs Postgres, Redis, daphne, a worker and beat; compose overrides `DB_*`/`REDIS_*` to the containers and requires `SECRET_KEY` and `DB_PASSWORD`. Code is baked into the image (no bind mount), so rebuild after changes. `scripts/healthcheck.py` sends the first `ALLOWED_HOSTS` entry as the Host header. 
- The workspace root (outside this repo) has a `docker-compose.yml` running IQ, m18 and the frontend together on one Postgres (databases `iq`, `m18`) and one Redis (IQ db 0, m18 db 1); each backend runs `migrate` then `manage.py seed --fixture /seed/<name>.json`. `seed` mutes model signals during `loaddata` (otherwise `sync/signals.py` creates `StockSyncState` rows that clash with the snapshot's).
- Dependencies live in a single `requirements.txt` (runtime plus test/lint tools; the Docker image installs it too). Settings support Postgres via `DB_ENGINE`/`DB_*`; the full test suite passes on both SQLite and Postgres.
- Tests build data with factories in `common/tests/factories.py`. A test acting as a user must create its data under `user.company`, otherwise the scoped API correctly hides it.
- `PriceRecommendationService.apply_decay_pricing` is idempotent: markdowns are computed from the pre-markdown price recorded in `PriceChangeLog`, so it is safe to run repeatedly.
- External services: AlAdhan (Hijri dates) and the UK Trade Tariff (duty) are public and verified live (`RUN_LIVE_TESTS=1 pytest common/tests/test_live_integrations.py`); the tariff service also resolves country-group preferences (EU, trade schemes) via `/geographical_areas/{group}`; Shopify is only covered by mocked tests. Shopify uses the GraphQL Admin API (the REST product/variant endpoints are deprecated) and `SHOPIFY_API_VERSION` must be kept on a supported version. `ShopifyConnection.shop_domain` is validated against `*.myshopify.com` because it becomes part of an outgoing request URL (SSRF). The tariff fixture `common/tests/fixtures/tariff_0804100099.json` is a trimmed real response.
- `SECRET_KEY` must be 32+ characters outside `DEBUG`, and the placeholder once committed to this public repo (checked by hash in `config/settings.py`) is refused.
- Human-entered identifiers must be unique per company, never globally (a global unique constraint lets one tenant detect another's data): `SupplierInvoice.invoice_number` is per company and `StockBatch.batch_number` per product. `SyncTask.task_id` is deliberately global: it is a system-generated id (read-only in the API) the Celery task looks up on its own. A company has at most one `ShopifyConnection`, and only company staff can change it.
