# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root. `SECRET_KEY` has no default and must be set (via `.env` or the environment), otherwise settings fail to import.

```bash
export SECRET_KEY=dev-secret          # or copy .env.example to .env
python manage.py migrate              # SQLite by default (db.sqlite3)
python manage.py runserver
python manage.py seed_demo_data       # idempotent demo company + owner (lives in tenants/)
python manage.py seed_cultural_events # idempotent placeholder CulturalEvents (lives in demand/)
python manage.py seed --fixture x.json  # snapshot into an empty DB + superuser from DJANGO_SUPERUSER_* (tenants/)

pytest                                # whole suite (use this, not `manage.py test`)
pytest authentication/tests.py::PasswordResetConfirmTests::test_valid_token_resets_password
pytest -k tenancy
pytest --cov=authentication --cov=common --cov-fail-under=70   # the CI gate

python manage.py makemigrations --check --dry-run
python manage.py spectacular --file schema.yml                 # OpenAPI; should print no errors/warnings
celery -A config worker -l info       # needs Redis; `celery -A config beat` for the schedule
ruff check .                          # CI lint step (config in ruff.toml)
```

`manage.py test` also works, but CI and the Makefile use pytest. A local `venv/` is git-ignored; API docs are served at `/api/docs/`.

## Architecture

Django 5.2+/DRF monolith. `config/` is only the project package (settings, urls, asgi, wsgi, celery); every app is a top-level directory. 

**Multi-tenancy is by company, not by schema.** `tenants.Company` is the tenant; `AUTH_USER_MODEL = tenants.CustomUser` (email login, has a `company` FK). `common/tenancy.py` is the single source of truth: `TENANT_LOOKUPS` maps each tenant-owned model to the ORM path reaching its company (e.g. `StockMovement -> batch__product__company`).
- Viewsets for tenant data must use `TenantScopedMixin` (filters the queryset, stamps `company` on create, requires a company) and serializers must extend `TenantModelSerializer` (limits related-object fields to the user's company, makes `company` read-only). Other companies' rows are 404, never 403.
- Adding a tenant-owned model means adding it to `TENANT_LOOKUPS`; a test in `common/tests/test_tenancy.py` fails if a lookup path is wrong.
- Shared reference data (`ProductCategory`, `CulturalEvent`, `PricingPlan`, `demand_calendar`) is unscoped: viewsets use `IsStaffOrReadOnly`.
- Superusers bypass scoping; users with no company get 403. The company always comes from `request.user.company` (loaded from the DB), never from a token claim.
- The Django admin is scoped the same way: `TenantAdminMixin`, applied to explicit admins and auto-registered for every other `TENANT_LOOKUPS` model in `common.apps.CommonConfig.ready()`; `CustomUser` has a dedicated `CustomUserAdmin` in `tenants/admin.py` that hides superusers, `is_superuser`, groups, permissions and `company` from company staff (anti-escalation; covered by `CustomUserAdminTests`).
- Default DRF permission is `IsAuthenticated`. Only login, password-reset confirm, invitation accept and verify-email-token are `AllowAny`.

**Auth.** `POST /auth/login/` returns a short-lived HS256 access token (signed with `SECRET_KEY`, `authentication/jwt_handler.py`) plus an opaque refresh token. `authentication.authentication.JWTAuthentication` is the first DRF authenticator, followed by session and basic; unauthenticated requests therefore get 401. Refresh tokens (`authentication/refresh_tokens.py`, model `RefreshToken`, only a SHA-256 stored) are single use: `POST /auth/token/refresh/` rotates within a "family", and replaying a used token revokes the family. Both token types embed/store a stamp of the password hash (`password_stamp`), so any password change invalidates every earlier token. `POST /auth/logout/` revokes a family; access tokens are stateless and live until expiry. Revocation must happen outside `transaction.atomic()` blocks that then raise, or it is rolled back. A token used again within `JWT_REFRESH_REUSE_LEEWAY_SECONDS` of being rotated (and only if the family was not ended by a logout/replay) is answered with a fresh pair instead of revoking the family, so two tabs can race; a session is hard-capped at `JWT_REFRESH_SESSION_MAX_AGE_SECONDS` (`session_started_at` is carried across rotations). A daily Celery task prunes dead tokens.

**API conventions.** Lists are paginated (`StandardResultsSetPagination`: `count/next/previous/results`, `page_size` capped at 100) and viewsets must have a deterministic order (the tenancy mixins fall back to `pk`). Non-validation errors are `{code, message, status_code}` via `common.exceptions.custom_exception_handler`; validation errors keep DRF's per-field shape.

**App layout.** Each app follows models / serializers / views (ModelViewSets) / urls (`DefaultRouter`). URL prefixes are in `config/urls.py` (`auth/`, `inventory/`, `sales/`, `demand/`, `calendar/`, `logistics/`, `pricing/`, `sync/`, `common/`). `common` also holds cross-app pieces: `DemandAlert`/`StockAlert` models, business `services/` (price recommendation, cost calculation, HMRC tariff, Hijri calendar, Shopify, verification tokens), the websocket consumer (`consumers.py`, `routing.py`), and `tenancy.py`.

**Background work.** Celery tasks live in each app's `tasks.py` (autodiscovered): `common` (low-stock and demand alerts), `logistics` (freight rates), `pricing` (`sync_approved_prices` pushes approved `PriceChangeLog`s to Shopify via `ShopifyService`), `sync`, `authentication` (prunes dead refresh tokens). The beat schedule is defined in `config/celery.py`. `config/__init__.py` imports the Celery app.

**Realtime.** `config/asgi.py` routes websockets through `common/routing.py` (`/ws/sync/`). The channel layer is in-memory unless `USE_REDIS_CHANNELS=True`.

**Demand planning.** `common.tasks.scan_demand_alerts` generates `DemandAlert`s from upcoming `demand_calendar.Event`s (product categories x multiplier) and `demand.CulturalEvent`s (products linked via `EventProductKeyword`, multiplier from the company's `cultural_event_multiplier` `Setting`); demand is estimated from outbound `StockMovement`s (`inventory/projections.py`, also behind `.../stock-projection/`). Alerts are unique per product and event, so the scan is idempotent. `GET /common/api/alerts/demand/` lists the company's alerts (open by default, `?status=handled|all`), `.../create/` and `.../dismiss/<pk>/` write them. `demand_calendar.sync_islamic_events` fills the calendar from `HijriCalendarService`.

**Point of sale.** The `sales` app runs the tills. A `TillSession` is a shift (open with a cash float, one open session per till, close with a cash count; `expected_cash` and the variance are frozen at close). A `Sale` is rung up against the open session (`POST /sales/sales/`, items are `{product, quantity}`; prices always come from `Product.price`; send a `client_ref` UUID so a retry after a lost response returns the original sale with 200 instead of charging twice): stock is taken from the product's batches oldest expiry first, expired batches are never sold, each take is an outbound `StockMovement`, and `SaleAllocation` remembers the batches so `POST /sales/sales/<id>/void/` can put the units back with inbound movements. Cash sales need `amount_tendered >= total` (change is computed); card sales don't. Voiding is for staff or the sale's own cashier, and only while the session is open; closing is for the opener or staff. Products with stock but no batch can't be sold. Business logic is in `sales/services.py`, not the views.

**Operators and roles.** Some people work in one area and sign in with an 8-digit code instead of an email and password: `CustomUser.role` is one of `till`, `demand`, `freight`, `supplier`, `stock` (`tenants/roles.py`; regular and staff users have no role and see everything their permissions allow). Staff create them at `POST /tenants/operators/ {name, role}`; the code is generated (never chosen, because a "taken" error would reveal other companies' codes), returned once, and stored only as an HMAC (`code_hash`, `tenants/operator_codes.py`), so a forgotten one is replaced with `POST .../<id>/reset-code/`. Resetting a code, changing a role (`PATCH`) or deactivating (`is_active`) ends the operator's sessions; operators are never deleted, so their work stays attributed. They sign in at `POST /auth/code-login/ {code}` (throttled harder than passwords, `CODE_LOGIN_THROTTLE_RATE`, 5/min) and get the normal token pair. `authentication/role_access.py` is a default-deny allow-list of what each role may call (e.g. freight: `/logistics/*`; supplier: suppliers, invoices; till: products, tills and its own sessions/sales); `JWTAuthentication` enforces it on every request, so a new endpoint is closed to operators until it is listed there, and tenancy plus each viewset's own permissions still apply. In `sales`, a till operator only sees their own sessions and sales. `GET /auth/me/` returns `role` and `role_label`.

**Importing products.** `python manage.py import_storefront_products [--company M18-DEMO] [--file saved.json] [--dry-run]` pulls the online shop's public product API into a company (`Product.external_id` is the shop's id, so re-runs update names/prices/descriptions but never stock). New products with stock get one `OPENING` batch (expiring `--expiry-days` from today; the shop publishes no expiry dates) so the till can sell them. Products with no price or marked inactive are skipped.

**Storefront (m18) integration.** The m18 shop is a separate service; nothing is shared but signed webhooks. A company has at most one `sync.StorefrontConnection` (its `webhook_secret` is set only in the admin and never shown again). The shop posts `order.paid` events to `POST /sync/inbound/storefront/<connection id>/` (`sync.views.StorefrontInboundView`). That route has no user: the only authentication is the `X-Integration-Signature` header (`sync/signing.py`, HMAC-SHA256 over `"<t>." + raw body`, 300 s window, kept in step with m18's `shop/integration/signing.py`), so it is outside `role_access` and the OpenAPI schema. A missing or inactive connection and a bad signature get the same 401. Each event is stored once as an `InboundEvent` (unique per connection and `event_id`), so a redelivery answers `{"status": "duplicate"}`. Items are matched by `Product.external_id` within the connection's company and taken with `inventory.ledger.take_fefo` (the same FEFO code the till uses). A validly signed event always gets 200, because the order is already paid: an unknown product or a malformed item is `unmatched`, too little stock takes what exists and is `partial`, and `detail` records each problem. Review them in the admin (`InboundEvent`, read-only). To rotate the secret, change it on the connection and on the shop's `IQ_WEBHOOK_SECRET` together; the shop redelivers anything rejected in between.

**Storefront loyalty at the till.** Loyalty accounts live in m18. `POST /sync/loyalty/lookup/` (`sync.loyalty.lookup`; the `till` role may call it) makes one signed call to the connection's `base_url` + `rewards/api/integration/lookup/` with a 1.5 s timeout: 503 `loyalty_unavailable` on a timeout or error (the till sells without points), 404 `not_found`, 409 `not_configured` with no active connection. Hits are cached 60 s under a hash of connection and card. A sale with a `loyalty_barcode` writes a `loyalty.award` `sync.OutboundEvent` in the sale's transaction (`sync.outbox.emit`), and a void writes `loyalty.reverse`; both use `order_reference` `iq-sale-<client_ref or sale pk>`, which m18 de-duplicates on. `emit` queues `sync.tasks.deliver_outbound_event` on commit (a broker failure is logged, never raised into the sale), and beat runs `deliver_outbound_events` every 30 s to retry with backoff `min(2**attempts, 3600)` s, `failed` after 20 attempts. Outbound events are read-only in the admin. This needs a Celery worker *and* beat for IQ (`celery -A config worker -B`, or separate beat); without beat a failed send is never retried. The backoff means a short m18 outage catches up within about 30 s, but after a long one the next attempt can be up to an hour away (≈1 h after attempt 12). In local runs, give IQ and m18 different Redis databases (`CELERY_BROKER_URL` vs m18's `REDIS_URL`), or each worker picks up the other's tasks.

**Storefront stock (IQ → m18).** IQ owns stock for products linked to the shop (`external_id` set, company has an active `StorefrontConnection` with a `base_url`). Online available = in-date batch stock − `Product.online_buffer` ("keep for shop"), never below 0 (`sync.stock.online_available`). Receivers in `sync/signals.py` (new `StockMovement`, `StockBatch` save/delete, `Product` save) mark the product's `sync.StockSyncState` pending in the same transaction (`sync.stock.mark_changed`, an upsert that never fails the caller's write). Note that `ledger.move` and the movement serializer change stock with `.update()`, so it is the `StockMovement` row that triggers this, not the batch. Beat runs `sync.tasks.push_storefront_stock` every 15 s: pending products go out as absolute snapshots `{"product_id", "online_available", "version"}` in `stock.changed` outbox events (500 per event; `version` +1 per send, so m18 ignores older ones). Events go to m18's single `integration/events/` endpoint. Nightly at 00:30 UTC, `reconcile_storefront_stock` fetches m18's figures (`integration/stock/`), stores a read-only `StockReconciliation` report (`different` / `missing_in_m18` / `not_linked_in_iq`), then queues every linked product so the next sweep resends all (fixing drift and overnight expiry). First rollout: `manage.py push_storefront_stock`.

**Storefront prices (IQ → m18).** With `StorefrontConnection.push_prices` on (default off; switching it on in the admin queues every linked product), each `stock.changed` item also carries `"price": "12.99"` = `Product.price`, so a price approved through `PriceChangeLog` (or edited any other way) reaches m18 on the next 15 s sweep under the same per-product version. m18 then owns nothing about that price: it blocks edits and skips the product in its EPOS CSV sync, and refuses prices outside 0 < p ≤ 999.99 (its column cap) for that item only. The nightly report adds `price_different` rows whenever m18 returns a price, on or off, so differences can be checked before switching on. `PriceChangeLog.is_processed` remains Shopify-only.

**Stock ledger.** `StockMovement` is append-only (create/list/retrieve; no edit or delete, and read-only in the admin). Creating one adds to or takes from `StockBatch.quantity` and `Product.stock_quantity` under a row lock, and an outbound movement larger than the batch is a 400. Fix a mistake with a new movement. Creating a batch does not change `Product.stock_quantity`.

**Pricing.** `PriceChangeLog` is a *request*: clients cannot set `is_approved`/`is_processed`/`old_price` or any of the decision fields. The server stamps `source` (`manual` from the API, `decay_markdown` from the nightly job) and `requested_by`. The `approve` action applies `new_price` to the product (409 if the price moved or the change was rejected) and only then does `sync_approved_prices` push it to Shopify; `reject` keeps the row (`is_rejected`, 409 once approved). Both lock the row, take an optional `{"note"}` and record `decided_by`/`decided_at`/`decision_note`; decided rows cannot be deleted (only pending ones can be withdrawn). Both are staff-only (`IsCompanyStaffOrReadOnly`) and closed to operators (not in `role_access`; the `stock` role may only read the list). `PriceRecommendationService.propose_decay_markdowns` (nightly) only proposes; one batch per product (the nearest to expiry) drives its price; it ignores rejected rows and skips a markdown already rejected at the same old/new price. Invoice files are validated by extension *and* magic bytes, stored under a random name, and served only by an authenticated endpoint.

**Per-company uniqueness.** `TenantModelSerializer` also checks unique constraints that include `company` (DRF skips them because `company` is read-only), so use `UniqueConstraint(fields=['company', ...])` and the duplicate becomes a clean 400.

**Email.** `authentication/emails.py` sends invitation and password-reset links (templates in `settings.INVITATION_ACCEPT_URL` / `PASSWORD_RESET_URL`); a mail outage is logged, never raised.

**Encrypted fields.** `common.fields.EncryptedTextField` (Fernet, keys from `FIELD_ENCRYPTION_KEYS`, falling back to a key derived from `SECRET_KEY`) is used for `ShopifyConnection.access_token`; it cannot be filtered on, and legacy plaintext values still read fine.

**Static files** are served by WhiteNoise (`STATIC_ROOT=staticfiles/`, collected in the Docker build).

**Settings** read everything through `python-decouple` (`.env`). External-service settings (`HMRC_*`, `FREIGHT_RATES_API_URL`, `RATE_CHANGE_THRESHOLD`, `DEFAULT_CUSTOMS_DUTY_RATE`, `REDIS_*`) are listed in `.env.example`.

## CI/CD

GitHub Actions only (there is no CircleCI config). `ci.yml` has `test` (Postgres, missing-migration check, coverage gate), `lint` and `docker` jobs. `deploy.yml` runs via `workflow_run` after CI passes on `main`: build, push to ECR (tag = commit SHA), rewrite the ECS task definition's images with `jq`, update the service. It skips with a warning unless `AWS_ROLE_ARN`, `AWS_ECR_REPOSITORY_URL`, `AWS_ECS_CLUSTER`, `AWS_ECS_SERVICE` (secrets) and `AWS_REGION` (variable) are set. With the repository variable `ECS_RUN_MIGRATIONS=true` it first runs `migrate` as a one-off ECS task on the new revision (reusing the service's network config) and aborts the deploy if that fails; it always enables the ECS circuit breaker and fails the job unless the NEW task definition is the PRIMARY deployment with `rolloutState=COMPLETED` (a rolled-back service otherwise looks stable). The shell blocks were verified with a stand-in `aws` CLI, not real AWS. Validate workflow edits with `docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest`. Setup details are in the README.

## Gotchas

- Migrations are a fresh initial set; most apps have a `0001_initial` plus `0002_initial` because of cross-app foreign keys (`authentication` and `sync` add later migrations on top). Delete any old local DB rather than migrating it forward.
- Docker: `docker compose up --build` runs Postgres, Redis, daphne, a worker and beat; compose overrides `DB_*`/`REDIS_*` to the containers and requires `SECRET_KEY` and `DB_PASSWORD`. Code is baked into the image (no bind mount), so rebuild after changes. `scripts/healthcheck.py` sends the first `ALLOWED_HOSTS` entry as the Host header. 
- The workspace root (outside this repo) has a `docker-compose.yml` running IQ, m18 and the frontend together on one Postgres (databases `iq`, `m18`) and one Redis (IQ db 0, m18 db 1); each backend runs `migrate` then `manage.py seed --fixture /seed/<name>.json`. `seed` mutes model signals during `loaddata` (otherwise `sync/signals.py` creates `StockSyncState` rows that clash with the snapshot's).
- Dependencies live in a single `requirements.txt` (runtime plus test/lint tools; the Docker image installs it too). Settings support Postgres via `DB_ENGINE`/`DB_*`; the full test suite passes on both SQLite and Postgres.
- Tests build data with factories in `common/tests/factories.py`. A test acting as a user must create its data under `user.company`, otherwise the scoped API correctly hides it.
- `PriceRecommendationService.apply_decay_pricing` is idempotent: markdowns are computed from the pre-markdown price recorded in `PriceChangeLog`, so it is safe to run repeatedly.
- External services: AlAdhan (Hijri dates) and the UK Trade Tariff (duty) are public and verified live (`RUN_LIVE_TESTS=1 pytest common/tests/test_live_integrations.py`); the tariff service also resolves country-group preferences (EU, trade schemes) via `/geographical_areas/{group}`; Shopify is only covered by mocked tests. Shopify uses the GraphQL Admin API (the REST product/variant endpoints are deprecated) and `SHOPIFY_API_VERSION` must be kept on a supported version. `ShopifyConnection.shop_domain` is validated against `*.myshopify.com` because it becomes part of an outgoing request URL (SSRF). The tariff fixture `common/tests/fixtures/tariff_0804100099.json` is a trimmed real response.
- `SECRET_KEY` must be 32+ characters outside `DEBUG`, and the placeholder once committed to this public repo (checked by hash in `config/settings.py`) is refused.
- Human-entered identifiers must be unique per company, never globally (a global unique constraint lets one tenant detect another's data): `SupplierInvoice.invoice_number` is per company and `StockBatch.batch_number` per product. `SyncTask.task_id` is deliberately global: it is a system-generated id (read-only in the API) the Celery task looks up on its own. A company has at most one `ShopifyConnection`, and only company staff can change it.

## Where things go in this repo
- New domain apps are top-level directories; `config/` is only settings.
- Stock changes: `inventory/ledger.py` only. Till logic: `sales/services.py`.
- Cross-service code: `sync/` (signing, outbox, inbox, tasks).
- Roles: `authentication/role_access.py`. Tenancy: `common/tenancy.py`.
- Scheduled jobs: add to the Celery beat schedule and to the job table in README.
- Tests: pytest, next to the app (`<app>/tests/`). Live external-API tests stay opt-in.
